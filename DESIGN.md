# spanbolt

A fast, drop-in replacement for the Cloud Spanner emulator, for tests and CI.

## Goals

1. **Drop-in.** Same gRPC API (`google.spanner.v1`, `google.spanner.admin.{database,instance}.v1`,
   `google.longrunning`) on port 9010, REST admin on 9020 later. Clients connect with
   `SPANNER_EMULATOR_HOST` unchanged: Java client, Spanner JDBC (Liquibase), Python, Beam SpannerIO.
2. **Fast startup.** Process ready in < 50 ms. Loading a snapshot file is near-instant.
3. **Fast runtime.** Point reads and single-row commits well under 1 ms in-process; index-backed
   lookups (never a full scan when a key or index prefix applies); no per-statement catalog rebuild.
4. **Real concurrency.** Many read-write transactions at once. Non-conflicting transactions never abort.
5. **Persistence and snapshots.** Save a whole instance to a file and load it back. A Docker image
   with a pre-seeded snapshot is just the binary plus that file.
6. **`CloneDatabase` in O(1).** Copy-on-write clone of a database, so every test class (or test) gets
   a fresh database from a seeded template in microseconds.
7. **Prod fidelity.** GoogleSQL semantics come from Google's own analyser (see SQL below). Anything we
   do not support fails with `UNIMPLEMENTED`, never a silently different answer. A strict mode
   rejects what real Spanner rejects (e.g. NULL_FILTERED index used without `IS NOT NULL`).
8. **Test controls.** Settable clock; deterministic `ABORTED` injection; per-query timing.

## Architecture

```
clients ──gRPC──▶ spanbolt-server (tonic)
                     │
                     ├── sessions, transactions (spanbolt-txn)
                     ├── DDL parser + schema model (spanbolt-ddl)
                     ├── SQL: GoogleSQL analyser (C++, FFI) ─▶ resolved AST ─▶ Rust executor (spanbolt-sql)
                     └── storage (spanbolt-storage): persistent maps, MVCC versions, snapshot files
```

### Storage (`crates/storage`)

- Values: `Value` enum covering Spanner types: BOOL, INT64, FLOAT32, FLOAT64, NUMERIC, STRING, BYTES,
  DATE, TIMESTAMP, JSON, INTERVAL, UUID, TOKENLIST, ARRAY<T>, STRUCT (query-only), plus NULL.
- Keys: order-preserving byte encoding of the primary key (with per-column ASC/DESC), so tables and
  indexes are `imbl::OrdMap<KeyBytes, Row>` (persistent, structurally shared B-tree).
- A database state is an immutable `Arc<DbState>` (schema + tables + indexes). A commit builds a new
  state from the old one by structural sharing. MVCC = a short list of `(commit_ts, Arc<DbState>)`
  versions kept for stale/snapshot reads, pruned by a version-GC horizon.
- `CloneDatabase` = copy the `Arc` of the latest state. O(1).
- Snapshot file: serialize all databases (schema DDL + rows) with a compact binary format, zstd
  compressed. Loading rebuilds maps; target < 1 s for our ~500-table schema with seed data.

### Transactions (`crates/txn`)

- Optimistic concurrency, first-committer-wins. A read-write transaction records its read set
  (point keys and key ranges per table/index) and buffers writes. At commit, under a short per-database
  commit lock: if any commit since the transaction's start wrote a key in its read or write set,
  return `ABORTED` (clients retry); otherwise apply and assign a strictly increasing commit timestamp.
- Read-only / snapshot transactions read a pinned version without locks.
- DML inside a read-write transaction sees its own buffered writes (read-your-writes).
- Partitioned DML: executed as independent batches.
- Schema changes: serialized per database; they wait for in-flight commits, not for open transactions.

### DDL (`crates/ddl`)

- Hand-written parser for Spanner GoogleSQL DDL: CREATE/ALTER/DROP TABLE, INTERLEAVE IN PARENT
  (ON DELETE CASCADE), FOREIGN KEY, CHECK, generated/stored columns, DEFAULT, allow_commit_timestamp,
  ROW DELETION POLICY, CREATE [UNIQUE] [NULL_FILTERED] INDEX ... STORING ... INTERLEAVE IN,
  SEARCH INDEX, TOKENLIST columns, CHANGE STREAM, SEQUENCE, SCHEMA, VIEW, ROLE/GRANT (accepted and
  stored), PROPERTY GRAPH (accepted and stored), ALTER DATABASE options, synonyms.
- Schema model with validation (types, key columns, interleave parent key prefix, index columns).
- `GetDatabaseDdl` printer emitting the canonical form the official emulator emits.
- Fixture: `fixtures/schema.json` — 524 statements in GetDatabaseDdl form, generated by
  `cargo run -p spanbolt-ddl --example gen_schema` with the shape of a large production schema
  (261 tables, 249 indexes, views, change streams, a property graph; roles and grants in
  `access_ddl`). Every statement must parse, print identically, and round-trip.

### SQL (`crates/sql`, `native/googlesql`)

- GoogleSQL (github.com/google/googlesql, formerly ZetaSQL) analyses each query against a catalog
  built from our schema, and returns the resolved AST as a protobuf. Rust plans and executes it.
- Analysed statements are cached by (schema version, SQL text), so the analyser cost is paid once per
  distinct statement.
- Until the FFI exists, a minimal Rust SQL path may be used for bootstrapping tests only.

## Fidelity oracle

Differential tests: run the same DDL, mutations and queries against the official emulator
(`gcr.io/cloud-spanner-emulator/emulator:1.5.59`) and spanbolt, compare results and error codes.
Later, the same suite runs against real Spanner.

## Layout

```
crates/proto     generated googleapis types and tonic services
crates/storage   values, key encoding, tables, MVCC states, snapshot files
crates/txn       transaction manager
crates/ddl       DDL parser, schema model, DDL printer
crates/sql       SQL planning + execution
crates/server    tonic services + binary `spanbolt`
native/googlesql C++ shim around GoogleSQL exposing a C ABI
fixtures/        schema fixtures
```

## Rules

- Rust stable, edition 2024. `cargo fmt`, `cargo clippy -- -D warnings`, `cargo test` must pass.
- Commits use conventional commit format: `type(scope): description`.
- No `unwrap()` on request paths; map errors to proper gRPC status codes (INVALID_ARGUMENT,
  NOT_FOUND, ALREADY_EXISTS, FAILED_PRECONDITION, ABORTED, UNIMPLEMENTED) with Spanner's messages.
